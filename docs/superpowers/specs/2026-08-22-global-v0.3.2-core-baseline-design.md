# Global v0.3.2 Core Baseline Design

## Goal

Upgrade `gtm-listing-demo` from the v0.2.0 monolithic Skill to a global v0.3.2 execution baseline that inherits the generic workflow, production, evidence, hardening, and standalone-demo safeguards proven in `japan-listing-demo` through v0.3.2, while preserving the global repository's market / locale / region / channel / category / private-overlay separation and excluding Japan-specific rules.

## Source baseline

- Global source of truth before this change: `heymio/gtm-listing-demo@main`, commit `b882526f5a683235d30f562006cf1984a9f0d9f9`.
- Generic capability reference: `heymio/japan-listing-demo@v0.3.2` / current `main` after PR #11.
- The Japan repository is a reference implementation, not a file-copy source of truth. Every migrated capability must be generalized and checked for market / locale / channel leakage.

## Architecture

The global repository becomes a five-Skill execution system behind one normal invocation:

```text
$gtm-listing-demo
        ↓
Thin Router
        ↓
listing-planning      Stage 0–7
        ↓
listing-production    Stage 7.5–8
        ↓
listing-hardening     Stage 8.5–10
        ↓
listing-evidence-auditor
```

`gtm-listing-demo` remains the only normal user-facing invocation. Internal Skills are stage-local execution planes and must not force ordinary users to invoke them manually.

## Global configuration model must remain intact

The following global layers remain first-class and separate:

```text
Core Workflow
├── Channel Profile
├── Locale Profile
├── Region Overlay
├── Category Overlay
├── Brand / Private Overlay
└── Project Evidence
```

Rules:

1. `market`, `locale`, `region_overlays`, `channel`, `category`, `offer`, and `page_targets` remain distinct fields.
2. Locale profiles may define language and formatting but may not create consumer personas or message priorities without project evidence.
3. Region overlays may define cross-country verification obligations but may not replace country / locale research.
4. Channel profiles may define page structure, editable regions, interaction families, and capability contracts, but may not contain product-category selling points.
5. Category selling logic belongs only in category overlays, examples, evals, private overlays, or project evidence.
6. Private account / brand capabilities are never hard-coded into the public generic core.

## Generic capabilities to migrate

### 1. Checkpoint and anti-loop behavior

- Major Stage Checkpoints by default.
- Transition commands such as `continue`, `next`, `go`, and equivalent should advance the workflow rather than trigger unbounded re-explanation or regeneration.
- Two-attempt autonomous retry budget for the same asset / same identified problem unless new evidence or user direction arrives.
- Concise `Done / Open / Next` checkpoint summaries for normal transitions.

### 2. Complete planning handoff

Planning must end with formal state objects rather than forwarding the full conversation:

- Project Brief / Project Definition equivalent;
- Creative Strategy Kernel;
- Production Handoff;
- Complete Demo-Required Production Set;
- Page Visual System;
- per-asset Evidence Mode.

Priority proof coverage is not asset-set completeness. The final Demo-required asset set must be derived from the approved page architecture, not only from P0 messages or currently available images.

### 3. Page Visual System

Each final asset receives deliberate structured visual direction:

- `visual_role`
- `scene_family`
- `composition_family`
- `tone`
- `product_scale`
- `proof_form`
- optional `neighbor_contrast_note`

Core rule: `Same art direction != same composition`.

The Page Visual System belongs inside the existing Planning handoff. It is not a new numbered Stage or Hardening gate.

### 4. Evidence Mode

Every v0.3.2 final asset uses exactly one mode:

- `SOURCE_FAITHFUL`
- `CREATIVE_MOCK`
- `PROOF_VISUAL`

Product-identity requirements must be separated from proof-grade requirements.

- Missing product-identity source required to keep the actual product faithful blocks all relevant modes.
- `CREATIVE_MOCK` may continue with an explicit limitation when only proof-grade evidence is missing.
- `PROOF_VISUAL` and `SOURCE_FAITHFUL` block when their required authoritative proof / identity evidence is missing.

Generated environment details never become Product Truth.

### 5. Account Capability Profile

Generic channel/account capabilities may be reused when a persistent profile is recent, structurally valid, scoped to the intended account/channel, and non-conflicted. Missing, stale, malformed, or contradicted capability evidence must be re-verified.

No marketplace-specific entitlement or private brand value is hard-coded into the generic core.

### 6. Production Context Firewall

Production consumes only:

- Creative Strategy Kernel;
- Production Handoff;
- one current Asset Packet;
- referenced source assets;
- approved benchmarks / visual patterns.

A v0.3.2 one-job Asset Packet must include:

- exactly one Asset ID;
- one channel role / slot;
- one primary shopper task / message;
- output quantity 1;
- current Evidence Mode;
- current Page Visual System direction;
- nearest same-region / same-page-region neighbor summaries only.

Project State, auditor results, delivery parity, gate narration, or full conversation history must not leak into ordinary image-generation context.

### 7. Artifact-first visual production

When the user asks for one final visual asset, production must produce that artifact rather than replacing it with a workflow diagram, production map, asset ledger, or status infographic.

Gallery / PDP media / enhanced-content / DTC modules remain separate asset roles when their channel role differs, even if the marketing message overlaps.

### 8. Candidate history and Selection Lock

Every generated alternative is a distinct candidate. When a user selects an exact candidate:

- bind `selected_candidate_id`;
- bind exact `current_output_ref`;
- mark candidate `USER_SELECTED`;
- mark asset `USER_APPROVED`;
- preserve candidate history.

Until explicit reopen intent, the system may not:

- replace `current_output_ref`;
- add a new candidate;
- roll the asset back to `REVIEW` / `REVISE`;
- silently supersede the selected candidate.

### 9. Set-level Creative QA

Asset-level QA is necessary but not sufficient. Ordered visual sets must be reviewed for:

- scene repetition;
- composition repetition;
- tone / brightness rhythm;
- product-scale repetition;
- proof-form diversity;
- adjacent message-role redundancy.

A final whole-set / contact-sheet review is required before Production Freeze for v0.3.2 handoffs.

The final set review must bind:

- exact current required Asset IDs;
- exact current `current_output_ref` for every required asset;
- visual review reference;
- status `CLEAR` or explicit `USER_ACCEPTED`.

If any selected asset output changes after the review, the old whole-set review becomes stale.

### 10. Scope Delta and smallest sufficient cleanup

Production may apply removal-only scope changes when the user narrows the already-planned asset set. A removal must keep these views aligned:

- authoritative `asset_set`;
- page / region order;
- Page Visual System directions.

Adding an asset or changing role / message / evidence requirements returns to Planning for a revised handoff rather than inventing upstream decisions inside Production.

Cleanup defaults to the smallest sufficient intervention:

- single asset defect → reopen only affected asset;
- set repetition → preserve approved assets and reopen the smallest useful subset;
- evidence limitation on a valid `CREATIVE_MOCK` → preserve creative output when product identity remains source-faithful;
- all affected assets already approved → explicit user choice before reopening an approved asset.

### 11. Evidence auditor and exact-file trust boundary

The generic core adopts the independent evidence-auditor architecture:

- candidate registry is not trusted evidence state;
- physical file fingerprinting recomputes file identity;
- supported PNG / JPEG / WebP signatures, extensions, byte size, dimensions, and path containment are verified;
- human approval binds exact physical hash + approved role + slot/page/offer scope;
- same-name replacement does not inherit approval when bytes change;
- duplicate IDs fail fast before dictionary/index collapse;
- same-context semantic review cannot self-promote to independent trust.

When independent semantic review is unavailable, unresolved semantic-role evidence remains `UNVERIFIED` / `HUMAN_REVIEW_REQUIRED` unless resolved by appropriate human approval or genuinely independent review.

### 12. Hardening and delivery-state safeguards

Generic hardening owns:

- final physical-file identity;
- evidence audit;
- role / scope integrity;
- transform authorization;
- module / slot origin;
- frontend fidelity;
- Demo assembly;
- delivery parity;
- final technical QA.

Creative Approval is separate from Evidence Verification.

Production Freeze answers whether the complete creatively approved set is ready. Pre-Demo Asset Gate answers whether the exact final files are evidence-safe. One cannot substitute for the other.

### 13. Channel-native fidelity

Planning separates Platform Capability evidence from Frontend Visual evidence.

Official channel documentation cannot substitute for actual current consumer-facing layout evidence when reproducing a marketplace / retailer shell.

If native frontend fidelity cannot be supported, the Demo must fall back to a clearly labeled `Content Review Demo` rather than inventing channel chrome.

This rule is generic across Amazon sites, retailer PDPs, marketplaces, and DTC references.

### 14. Final Demo output contract

The final project Demo is delivered as exactly one standalone `.html` file.

Requirements:

- no Demo ZIP as the user-facing final deliverable;
- no adjacent `assets/` directory;
- images / media resources physically embedded as portable `data:` URIs when used;
- inline CSS;
- inline JavaScript;
- no external or local runtime asset dependency;
- literal session-only `blob:` resource dependencies rejected;
- mixed / external `srcset` rejected;
- planned carousel includes previous / next controls and verifiable inline wiring;
- responsive viewport and width breakpoint required;
- responsive image contract required.

Static validation is necessary but not sufficient. Final runtime QA requires browser verification at:

- 1440px desktop;
- 390px mobile.

At both widths verify:

- no horizontal overflow;
- no broken images;
- no clipped primary copy or controls;
- correct content order;
- correct image/text pairing;
- carousel works in both directions when present;
- Review Mode does not corrupt Consumer Mode layout.

If browser/runtime verification cannot be performed, mobile / interaction QA remains `BLOCKED`; source inspection alone cannot claim PASS.

## Global-specific behavior to retain

The global repository must continue supporting at minimum:

- multiple country markets;
- locales `ja-JP`, `en-US`, `de-DE`, `it-IT` plus custom locale profiles;
- Amazon generic, DTC, retailer PDP, and generic marketplace channels;
- EU common region overlay;
- optional category overlays;
- Single / Kit / Bundle / variant page boundaries;
- global market-evidence registry and anti-stereotype rules;
- domain-leakage validation.

## Explicit exclusions from the global core

Do not migrate as generic defaults:

- Japan consumer preference assumptions;
- Japanese copy-style rules beyond the existing `ja-JP` locale profile;
- Amazon.co.jp-specific module ceilings or account entitlements;
- Rakuten / Yahoo! Shopping platform rules unless they are introduced later as explicit optional global channel profiles;
- Japanese legal / regulatory requirements;
- Japan-specific frontend evidence;
- SwitchBot or any other company-private capability;
- Light Bars, S30 mini, or any product-specific facts / visuals / outcomes.

## Packaging

Provide two distribution modes:

1. one-install compatibility ZIP with `gtm-listing-demo` as the user-facing Skill and internal stage/audit Skills embedded for clients that install one Skill;
2. repository / Codex bundle containing the five sibling Skills.

The one-install package must document the single-context semantic-audit limitation and must not claim independent semantic review merely because the auditor code is bundled.

## Version

Target global version: `0.3.2`.

## Acceptance criteria

1. Existing global multi-market / multi-locale / multi-channel validation remains green.
2. Generic regressions corresponding to Japan v0.2.2–v0.3.2 safeguards are present and executable.
3. No Japan-, Amazon.co.jp-, SwitchBot-, or product-specific rule leaks into generic core files.
4. Planning, Production, Hardening, Evidence Auditor, Router, and Project State test suites pass.
5. Standalone HTML validator/selftests pass.
6. One-install compatibility package builds and smoke-tests successfully.
7. Codex / repository bundle builds successfully.
8. Final changes are proposed through a Draft PR; no automatic merge.
